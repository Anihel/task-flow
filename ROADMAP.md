# TaskFlow — план разработки

## ✔ Этап 1. Зафиксировать правила предметной области

**Результат этапа:** правила записаны в README и не противоречат друг другу.

## Этап 2. Подготовить локальную разработку

- Вынести пароль базы из конфигурации в переменную окружения; не хранить секреты в Git.
- Добавить в README команды запуска приложения и базы, а также используемые адрес, порт и имя базы без секретов.

**Результат этапа:** приложение и база воспроизводимо запускаются по инструкции из README.

## Этап 3. Спроектировать схему данных

Согласовать сущности и связи до написания SQL:

- `project` — существующая таблица проектов;
- `users` — учётные записи пользователей;
- `project_members` — принадлежность пользователей проектам и, если нужно, роль в проекте;
- `tasks` — задачи проекта, со статусом, сроком и необязательными исполнителями.
- `task_assignees` — связи между задачами и исполнителями.

Для полей определить nullability, уникальность, внешние ключи и поведение удаления. Например, исполнитель задачи должен быть участником того же проекта — это правило нужно обеспечить на уровне приложения, а где возможно, дополнить ограничениями базы.

Добавлять каждое изменение отдельной версионной миграцией (`V2__...sql`, `V3__...sql` и так далее). Точные номера и порядок выбрать после сверки с текущей историей `flyway_schema_history`.

**Результат этапа:** пустая база полностью создаётся миграциями, а ограничения БД защищают целостность данных.

## Этап 4. Реализовать вертикальный срез проектов

Реализовать путь от HTTP-запроса до PostgreSQL:

1. Создание проекта.
2. Получение проекта по ID.
3. Получение списка проектов.

Использовать отдельные DTO для запросов и ответов API; разместить бизнес-логику в сервисном слое, а доступ к данным — в репозиториях.

**Результат этапа:** основные операции с проектами работают через API и покрыты тестами.

## Этап 5. Реализовать пользователей и доступ

- Добавить создание пользователей и уникальность email.
- Пароли хранить только в виде стойкого хеша, никогда не сохранять исходный пароль.
- Подключить Spring Security и выбрать способ аутентификации под клиента приложения.
- Проверять доступ к каждому проекту и его задачам на сервере; не полагаться на то, что пользователь не угадает ID.
- Добавить операции добавления и удаления участников проекта.

Не вводить JWT только по привычке: сначала определить, будет ли клиент браузерным приложением, мобильным приложением или только API.

**Результат этапа:** пользователь не может просматривать или изменять данные чужого проекта.

## Этап 6. Реализовать задачи

Добавлять функциональность постепенно:

1. Создание задачи в проекте.
2. Получение задачи и списка задач проекта.
3. Изменение названия, описания и срока.
4. Назначение исполнителей из участников проекта.
5. Изменение статуса.
6. Фильтрация списка по статусу и исполнителям.

Добавить валидацию входных данных и единый формат ошибок. Использовать подходящие HTTP-коды, например `400` для некорректного запроса и `404` для отсутствующего ресурса.

**Результат этапа:** основной сценарий MVP выполняется целиком: создать проект, добавить участников, создать задачу, назначить исполнителя или исполнителей и изменить статус.

## Этап 7. Тестирование

- Unit-тестами проверить бизнес-правила сервисов.
- Интеграционными тестами проверить API, PostgreSQL и применение миграций.
- Для изолированных интеграционных тестов рассмотреть Testcontainers.
- Проверить создание схемы на пустой базе, а не только работу с уже подготовленной локальной БД.
- Проверить отрицательные сценарии: недопустимый статус, чужой проект, несуществующий исполнитель, некорректные даты.

**Результат этапа:** ключевые правила и API-сценарии автоматически проверяются тестами.

## Этап 8. Автоматизация и документация

- Добавить GitHub Actions для сборки и запуска тестов при push и pull request.
- Документировать REST API через OpenAPI после появления основных эндпоинтов.
- В README описать назначение, MVP, стек и запуск проекта.
- По мере изменения решений обновлять этот план и README.

**Результат этапа:** CI проверяет изменения, а новый разработчик может понять API и запустить проект.

## После MVP

После завершения основного сценария выбрать одну следующую функцию, например историю изменений, комментарии, пагинацию, поиск или уведомления. Не добавлять инфраструктурные технологии без конкретной потребности.
